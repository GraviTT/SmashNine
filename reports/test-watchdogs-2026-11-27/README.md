# 긴 검사의 감시를 프레임 수로 (2026-11-27, 시스템 담당)

총괄 결정: 긴 검사의 감시 타이머를 실제 시간에서 프레임 수로 바꾼다. 한도는 예전 초 한도를 60프레임/초로 옮긴 값이다 (240초 → 14,400프레임). 실제로 느슨해지면 안 된다. 바꾼 검사마다 일부러 준 부하에서 통과하는 것을 보인다.
표시: [잼] 잰 값, [코드] 코드를 읽고 안 것, [추정] 짐작.

## 한 줄 요약

- 오늘 이 PC가 바쁠 때 긴 검사가 실제 시간 감시에 걸려 실패했다. test_story_flow는 240초를 넘겼고, 따로 돌리면 110초에 통과했다. test_practice_mode는 저녁 부하에서 640초가 걸렸다 (예전 한도 540초).
- 이제 `tests/support/frame_watchdog.gd`가 process 프레임을 센다. 검사 네 개를 바꿨다: story_flow, practice_mode, frontend_flow, freed_targets.
- 일부러 준 부하에서 네 검사 모두 새 감시로 통과했다. 같은 부하에서 story_flow의 예전 감시는 249초에 실패했다 [잼].
- 연습 모드 기술 목록 검사가 구조가 바뀌면 조용히 덜 세던 것을 고쳤다. 이제 개수를 확인한다 (793 → 871개).

## 1. 왜 물리 시계가 아니라 프레임인가

- 엔진은 프레임이 늦으면 한 프레임에 물리 스텝을 여러 번(최대 8) 돌려 따라잡는다. 그래서 웬만한 부하에서는 물리 시계도 실제 시간과 같이 간다 (총괄 지적).
- 검사는 `_frames()`처럼 프레임마다 나아간다. 부하가 있으면 같은 프레임을 쓰는 데 실제 시간이 더 걸린다. 그래서 실제 시간이나 물리 시계로 감시하면 부하 때문에 걸린다.
- 프레임으로 세면, 경기처럼 게임 시간으로 가는 구간은 부하가 있을 때 오히려 프레임이 준다 (한 프레임에 물리가 더 나아감). 그래서 프레임 감시는 진짜 멈춤에서만 걸린다 [추정, 4절의 부하 확인과 맞음].
- test_luna_kit(3816f963)은 감시가 아니었다. 검사 안에서 게임 지속 시간(기술 창)을 재는 시계를 물리 시계로 바꾼 것이다. 그래서 이번 일의 근거로 쓰지 않는다.
- 아주 무거우면 (한 프레임에 133 ms가 넘음, 물리 8스텝으로도 못 따라잡음) 엔진이 자기 시계도 늦춘다. 이때는 예전 감시도 실제 시간보다 늦게 걸린다 (4절 frontend_flow).

## 2. 한도가 느슨해지지 않는가

- headless는 프레임이 가벼우면 초당 약 114프레임으로 돈다 [잼, `tests/analysis/lead/headless_frame_rate_probe.gd`: 빈 트리 113.9, 타이틀 화면 113.0]. 창이 없을 때의 잠(6.9 ms) 때문이다 [코드].
- 그래서 PC가 한가할 때 "초 × 60" 프레임 한도는 예전 초 한도와 같은 때나 그보다 먼저 걸린다. 부하가 있을 때만 프레임을 기다린다.
- 검사마다 정상 실행이 쓰는 프레임 수가 한도 안에 넉넉한지 봤다 (3절 표).

## 3. 조사: 실제 시간 감시를 쓰던 검사 9개 [잼]

PC가 꽤 조용할 때(CPU 7~50%) 정상 실행(run_all과 같은 방식)과 `--fixed-fps 60`으로 쟀다. 프레임은 `--print-fps`의 초당 수를 더한 값이다 (±1초).

| 검사 | 예전 한도 | 정상 실행 | 한도 대비 | 정상 실행 프레임 | 고정 60fps 프레임 | 새 한도 | 처리 |
|---|---|---|---|---|---|---|---|
| test_story_flow | 240초 | 81초 | 34% | 약 5,860 | 약 2,760 | 14,400 | 바꿈 |
| test_practice_mode | 540초 | 183초 | 34% | 약 20,700 | 약 9,090 | 32,400 | 바꿈 |
| test_frontend_flow | 90초 | 27초 | 30% | 약 590 | 약 590 | 5,400 | 바꿈 |
| test_freed_targets | 540초 | 113초 | 21% | 약 13,710 | 약 4,510 | 32,400 | 바꿈 |
| test_audio | 100초 | 16초 | 16% | 약 715 | (고정 fps에서는 소리 때문에 못 돔) | - | 그대로 |
| test_story_rewards | 45초 | 7초 | 16% | 짧음 | 짧음 | - | 그대로 |
| test_story_late_flow | 240초 | 30초 | 13% | 약 1,600 | 약 775 | - | 그대로 |
| test_gamepad | 420초 | 36초 | 8% | 약 3,245 | 약 1,336 | - | 그대로 |
| test_language | 90초 | 8초 | 8% | 짧음 | 짧음 | - | 그대로 |

- 오늘 부하는 검사를 약 3배 느리게 했다. 그래서 조용할 때 한도의 20% 이상을 쓰는 네 개를 바꿨다. 나머지 다섯은 6배 이상 남아서 그대로 뒀다. test_audio는 소리를 실제 시간으로 재는 검사라 원래 실제 시간이 맞다.
- 남는 폭이 가장 작은 것은 practice_mode다. 정상 실행 약 20,700프레임 대 한도 32,400으로 1.57배다. 검사가 크게 늘면 다시 본다.

## 4. 일부러 준 부하에서 [잼]

- 방식: 예전 판(main의 파일 사본)과 새 판을 나란히 돌렸다. 각각 코어 하나에 묶고, 같은 코어에 바쁜 프로세스 2개를 같이 묶었다 (예전 판 1번 코어, 새 판 2번 코어). 나머지 코어 둘은 다른 세션이 쓰게 남겼다. 18:19~18:45.

| 검사 | 예전 감시 (실제 시간) | 새 감시 (프레임) |
|---|---|---|
| test_story_flow | **실패: 249초에 timed out** | 통과, 541초 |
| test_frontend_flow | 통과, 531초 | 통과, 516초 |
| test_freed_targets | 통과, 135초 | 통과, 134초 |
| test_practice_mode | 통과, 339초 | 통과, 327초 |

- 새 감시는 네 검사 모두 부하에서 통과했다. story_flow는 예전 감시로는 같은 부하에서 실패했다.
- practice_mode의 예전 감시는 이 부하에서는 통과했다 (339초). 하지만 저녁의 보통 부하에서는 640초가 걸렸다 (예전 한도 540초를 넘음, 새 감시로 통과, 고정 fps 프레임 수는 병합 전과 같은 약 8,870). 실제로 걸릴 판이 있었다는 근거다.
- frontend_flow는 이 부하에서 약 20배 느려졌다 (27 → 516초). 예전 90초 감시도 걸리지 않았다. 정상 실행이 590프레임에 27초(프레임당 평균 45 ms)인 것은 메뉴 프레임이 무거워서가 아니다. 이 검사는 Main 장면을 열 번 가까이 다시 읽고, 한 번 읽는 데 2.8~3.7초가 든다. 메뉴 프레임 자체는 약 7.8 ms로 빈 장면(6.9 ms)보다 약 0.9 ms 더 든다 [잼, UI 담당 `tests/analysis/ui_audit/menu_frame_probe.gd`, headless]. 부하에서 많이 느려진 것은 장면 읽기(디스크·파싱)가 코어를 많이 써서로 본다 [추정]. 그 읽기 프레임이 133 ms를 넘어서 엔진이 자기 시계를 늦췄고, 그래서 예전 감시가 걸리지 않은 것으로 본다 [추정].
- 처음에는 PC 전체에 바쁜 프로세스 12개를 띄웠다. 다른 세션의 import와 4분 겹쳐서 멈췄고, 그 부하는 엔진이 시계를 늦추는 수준이라 맞는 시험도 아니었다. 그래서 코어에 가두는 방식으로 바꿨다.

## 5. 연습 모드 기술 목록 검사

- UI 담당이 키 글자를 판 위에 올리자, `_test_skill_list`가 패널의 직접 자식 라벨만 세서 54개 확인을 실패 없이 빠뜨렸다. 시스템 담당이 확인 수 차이(793 대 739)를 보고 물었고, UI 담당이 원인을 찾았다.
- 이제는 라벨을 깊이와 상관없이 모은다. 맞음 확인은 패널의 전역 사각형 기준이다. 그리고 개수를 확인한다: 라벨 수가 3 + 2 × 기술 수 이상인지, 키 J·K·L·(U)·I가 각각 제 라벨에 있는지, x=128 줄 칸이 기술 수와 같은지. 확인 793 → 871개. UI 담당이 새 구조(c701fcc7, a6b49051)와 맞는지 봤다.

## 6. 모든 세션이 따를 것

- 새 긴 검사의 멈춤 감시는 `FRAME_WATCHDOG.start(self, 초, "문구")`로 건다. 실제 시간 `create_timer`로 걸지 않는다.
- 검사 안에서 게임 속 지속 시간을 잴 때는 물리 시계를 쓴다 (test_luna_kit의 `_seconds()`).
- 개수가 정해진 것을 돌며 확인할 때는 개수도 확인한다. 구조가 바뀌면 조용히 덜 세지 않고 실패하게 한다.
