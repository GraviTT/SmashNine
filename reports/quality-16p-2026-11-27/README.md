# 16인과 성능: 측정, 고친 것, 추천 (2026-11-27, 시스템 담당)

품질 트랙 ④ (D53). 목표는 `reports/quality-systems-2026-11-24/` 2-4절과 같다: 솔로 16인, 물리 프레임 P95 ≤ 16.7 ms를 데스크톱과 웹에서 잰다.
표시: [잼] 잰 값, [코드] 코드를 읽고 안 것, [추정] 짐작.

> **아직 덜 된 부분:** 웹 숫자(4절)와 고침 후 데스크톱 절대값은 PC가 조용할 때 재서 채운다. 1~3절과 두 고침은 main에 들어간다.

## 한 줄 요약

- **데스크톱 CPU만 보면 16인도 목표 안이다.** 16인 P95는 13.1~13.4 ms, 8인은 8.8~9.8 ms다 [잼]. 다만 12명 이상이 살아 있는 구간은 P95가 약 15 ms이고, P99는 17~19 ms로 목표를 넘는다.
- **봇 패널을 숨기면 16인 P95가 26~27 ms로 두 배가 됐다.** 원인을 찾아 고쳤다 (3-1절). 시험용 패널을 끄는 플레이어 판에서 0.1초마다 한 번 끊김이 날 뻔했다.
- **웹 콘솔 경고 `bufferSubData: no buffer`는 Godot 4.7 엔진 버그였다.** 우리 쪽 방아쇠(컨베이어 화살표 표시)는 고쳤다 (3-2절).
- 16인을 선택지(지금 4·6·8)에 넣을지와 기본값은 **사용자가 정한다.** 추천은 웹 숫자를 본 뒤에 쓴다 (5절).

## 2. 16인이 바꾸는 것

경기 흐름은 같은 시드면 부하와 상관없이 같은 경기라서, 바쁜 시간에 돌린 판의 흐름 숫자도 쓴다 (프레임 시간은 쓰지 않음). 16인은 시드 3001~3007의 7판, 8인은 시드 3001~3003의 3판이다. **판 수가 적어 방향만 본다.**

| 항목 | 8인 (3판) | 16인 (7판) | 근거 |
|---|---|---|---|
| 시작 위치 | 구석 왕국 4곳에 2명씩 | 구석 4곳과 가장자리 4곳에 2명씩, 중앙은 비어서 시작 | [코드] `Main._spawn_players` |
| 경기 길이, 중앙값 (범위) | 270초 (4:12~4:54) | 271초 (4:23~5:08) | [잼] 방향만 |
| 첫 탈락, 중앙값 (범위) | 66초 (60~114) | 51초 (34~70) | [잼] 방향만 |
| 링아웃, 중앙값 (범위) | 11 (6~18) | 29 (25~37) | [잼] 방향만 |
| 1인당 받은 카드, 평균 | 2.46장 | 2.30장 | [잼] 방향만 |

- **경기 길이는 거의 같다.** 단계 시간표가 같아서다 [추정]. 사람이 늘어난 만큼 일찍, 많이 떨어진다 (링아웃이 약 2.5배).
- **카드 흐름은 거의 같다.** 1인당 카드는 16인이 평균 0.16장 적다. 이 차이는 잡음 안일 수 있다 (봇 판 하나의 순위가 카드 뽑기만으로 0.5~0.7 흔들린다, 11-26 측정).
- 11-24의 8인 8판(중앙값 5:08)과는 시드와 게임 판이 달라서 맞대지 않는다.
- **결과 화면이 열리는 한 프레임이 길다 [잼]:** 16인 44~54 ms, 8인 34~39 ms. 경기가 끝나고 결과표를 만드는 프레임 하나다. 플레이 중이 아니라서 지금은 고치지 않는다.
- **화면에서 확인할 것 (아직 안 봄):** 봇 패널이 16줄이 된다 (1280×720에서 높이가 맞는지), 미니맵의 왕국별 인원 숫자, 결과표 16줄. 웹 측정 때 같이 본다.

## 3. 찾아서 고친 것

### 3-1. 봇 패널을 숨기면 0.1초마다 얼굴 16개를 디스크에서 다시 읽었다

- **증상 [잼]:** 같은 경기에서 패널을 숨기면 16인 P95가 26.1/26.2/25.9/27.0 ms였다 (4판). 보이면 13.4~15.8 ms였다. 0.1초마다 오는 패널 새로고침 프레임만 비쌌다. 그 프레임의 P50이 숨김 25.0 ms, 보임 11.3 ms였고, 나머지 프레임은 둘 다 5.8~5.9 ms였다.
- **원인 [잼]:** `Main._bot_panel_rows()`가 0.1초마다 모든 선수의 얼굴을 `ArtSettings.character_portrait`로 다시 찾는다. 패널이 보이면 패널 칸이 그림을 쥐고 있어서 캐시에서 바로 나온다 (한 번에 0.02~0.15 ms). 숨기면 아무도 쥐지 않아서 새로고침이 끝나면 그림이 풀려나고, 다음 새로고침 때 디스크에서 다시 읽는다 (얼굴 하나 3.5 ms). `tests/analysis/lead/portrait_cost_probe.gd`로 쟀다.
- **처음 시험한 고침 (버림):** ArtSettings 안에 찾은 얼굴을 계속 저장했다. 숨김 판 P95가 27.0 → 10.9 ms가 됐다 [잼]. 하지만 `test_story_faces`가 실패했다. 그 검사는 실행 중에 얼굴 그림을 바꿔 넣는다. 그래서 되돌렸다.
- **넣은 고침 (Main.gd만):** (가) 패널이 숨겨져 있으면 줄을 만들지 않는다. 숨긴 패널은 원래도 줄을 읽지 않고 버렸다. (나) 패널 줄과 화면 밖 화살표(매 프레임)가 쓰는 얼굴을 Main 안에 캐릭터·몸별로 저장한다. 화면에 보이는 것은 같다.
- **전후 숫자** [잼, 부하 아래, 같은 판 비교]: 16:30 측정은 사용자의 Android Studio 빌드(CPU 100%)와 겹쳤다. 그래서 절대값 대신 같은 판 안에서 새로고침 프레임과 나머지 프레임을 맞댄다 (16인, 시드 3001, 패널 숨김).

| | 새로고침 프레임 P50 | 나머지 프레임 P50 | 차이 |
|---|---|---|---|
| 고침 전 (main) | 25.53 ms | 6.06 ms | +19.5 ms |
| 고침 후 | 14.40 ms | 14.26 ms | +0.1 ms |

  숨긴 패널이 0.1초마다 튀던 것은 없어졌다. 고침 후의 절대값(나머지 프레임 14 ms)은 빌드 부하 때문에 쓰지 않는다. 조용할 때 다시 잰다. 고침 전 두 판은 오후 값(새로고침 25.0, 보임 P95 13.4~15.8)을 되풀이했다.

### 3-2. 웹 콘솔 경고 두 가지

| 경고 | 언제 | 원인 | 처리 |
|---|---|---|---|
| `Framebuffer is incomplete: Attachment has zero size` | 숨은 창에서 크기를 주기 전 첫 로드에 한 번 | 캔버스 크기 0×0 [잼] | 우리 코드 아님 |
| `bufferSubData: no buffer`, 짝으로 `bindBuffer: element array buffers can not be bound to a different target` | 경기 중에만. 크기가 있는 캔버스(1920×1080)에서도 나옴. 타이틀 화면 335프레임 동안 0개 [잼] | Godot 4.7 엔진 버그 [코드]. 우리 쪽 방아쇠는 컨베이어 화살표 표시 | 방아쇠 고침 |

- **엔진 쪽 [코드]:** Godot 4.7의 Polygon2D는 모양이 같은 채로 다시 그려지면 메시를 제자리에서 고친다 (정점 → 색 → 인덱스). GLES3의 `mesh_surface_update_index_region`이 인덱스 버퍼를 `GL_ARRAY_BUFFER`에 묶는다. 데스크톱 OpenGL은 받아 주지만 WebGL은 거부한다 (4.7-stable 소스로 확인).
- **영향 [추정]:** 모양이 그대로라서 인덱스도 그대로다. 화면은 같을 것으로 본다. 다만 Chrome이 경고를 약 256개에서 끊어서("too many errors"), 그 뒤에 나는 진짜 WebGL 오류가 콘솔에 안 보이게 된다.
- **우리 쪽 방아쇠 [잼]:** 거부된 묶기 바로 앞에 올린 정점 데이터로 모양을 찾았다. 152개 중 151개가 `RealmHazards`의 컨베이어 화살표 표시(chevron, 크기 6)였다. `_update_belts`가 매 프레임 표시의 visible을 켜고 꺼서, 다시 켜질 때마다 다시 그려졌다. 1개는 HUD의 화면 밖 화살표였다.
- **고침:** 벨트 밖의 표시를 숨기지 않고 투명하게 한다 (`self_modulate.a`, `82a576b4`). 보이는 모습과 규칙은 같다. HUD 화살표는 UI 담당이 색과 고리 색을 바뀔 때만 넣게 고쳤다 (`6026b98c`, main에 있음).
- **전후 [잼]** (측정용 웹 빌드, 4인 경기, 시드 3001, 패널 숨김, 거부된 묶기 수):

| 빌드 | 컨베이어 표시 | HUD 화살표 |
|---|---|---|
| 지금 main (`e5ef42b7`, 화살표 고침 있음) | 176프레임에 183개 (프레임마다 약 1개, 계속) | 1개 |
| main + 표시 고침 | 시작 때 벨트가 처음 보일 때 한 번 28개, 그 뒤 205프레임 동안 0개 | 1개 |

  남은 시작 때 28개는 경기마다 한 번이라 Chrome 한도(약 256개)를 채우지 않는다.
- **모든 세션이 따를 것 (엔진 버그는 우리가 못 고친다):** 모양이 같은 Polygon2D를 다시 그리게 하지 않는다. 다시 그릴 때마다 웹에서 경고가 하나씩 난다. 무엇이 다시 그리게 하는지는 `tests/analysis/lead/polygon_redraw_probe.gd`로 쟀다 [잼]:
  - 숨겼던 것을 다시 켜면(`visible`) 한 번 다시 그린다. 잠깐 안 보이게 할 때는 투명도(`self_modulate.a` 또는 `modulate.a`)를 쓴다. 투명도는 다시 그리지 않는다.
  - `color`나 `polygon`에 **같은 값을 넣어도** 한 번 다시 그린다. 매 프레임 넣지 말고 바뀔 때만 넣는다.
  - 위치, 회전, 크기(`position`, `rotation`, `scale`)는 다시 그리지 않는다.
- **콘솔 확인:** 웹에서 이 경고가 다시 보이면 새 방아쇠가 생긴 것이다. 거부된 묶기 바로 앞의 정점 데이터로 모양을 찾는 방법은 6절에 있다.

## 4. 웹 측정 (아직)

- **아직 못 쟀다.** 16:30~17:30 조용한 시간은 사용자의 Android Studio 빌드(java, ninja, clang++ 11~12개, node)로 CPU가 100%라 깨졌다. 총괄 결정으로 정해진 시간을 두지 않는다. PC가 조용할 때마다 되는 만큼 잰다. 조건: codex exec 0개, 다른 Godot 0개, 사용자 빌드(clang++·ninja·java) 없음, CPU 35% 아래가 세 번 연속. 조건이 깨지면 그 판은 표시하고 멈춘다.
- 창 모드 데스크톱 측정(사용자 화면에 창이 뜸)은 사용자 답이 없어서 하지 않았다 (총괄 결정). headless 값과 웹 값만 쓴다.
- 측정용 로컬 빌드(병합·배포하지 않음)로 봇 16명 경기를 띄운다. `Main._ready`에 측정 전용 고리를 넣어 내보내고 바로 뺐다. 주소가 `index.html?measure=16&seed=3001&panel=0`이면 그 경기가 100% 속도로 시작한다.
- 숨은 브라우저 창은 requestAnimationFrame을 돌리지 않는다. 그래서 페이지에 넣은 작은 스크립트가 Worker 타이머로 1/60초마다 프레임을 준다. 프레임마다 메인 루프 시간(물리, 스크립트, WebGL로 넘기기)을 잰다. GPU 자체의 시간은 들어가지 않는다. 게임 쪽 기록(살아 있는 수, 단계, 물리 스텝 수, 패널 새로고침)과 프레임 단위로 1:1 맞춘다. 4인 시험 3,431프레임에서 맞는 것을 확인했다 [잼].
- 잴 판: 지금 main(A)과 고침을 넣은 빌드(D) × 16인 × 패널 켬·끔, 그리고 A 8인.

## 6. 파일
